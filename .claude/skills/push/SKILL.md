# 작업한 것 올리기 — 팀원이 한 문장으로 부른다

팀원은 개발자가 아닐 수 있다. **git 용어로 되묻지 말고 알아서 수습한 뒤, 마지막에
「GitHub에서 이 링크를 눌러 PR을 만드세요」까지 알려 준다.**

## 먼저 상태를 본다

```
git branch --show-current
git status --short
git log --oneline -3
```

## 1. main에서 작업했다면 — 브랜치로 옮긴다

**`main`에는 직접 push할 수 없다** (저장소 보호 규칙). 팀원이 브랜치를 안 만들고 작업한
경우가 흔하므로 먼저 확인하고, 그렇다면 조용히 옮긴다.

**아직 커밋 전이면** — 브랜치를 새로 만들면 변경이 그대로 따라온다:

```
git switch -c part-(a~e)/(작업요약)
```

**이미 main에 커밋했으면** — 브랜치를 만들고 main은 원격 상태로 되돌린다:

```
git switch -c part-(a~e)/(작업요약)
git branch -f main origin/main
```

⚠️ `git branch -f main origin/main`은 **새 브랜치로 옮겨 온 뒤에** 실행한다.
순서가 바뀌면 커밋을 잃는다. 실행 전 `git log --oneline -3`으로 내 커밋이 새 브랜치에
있는지 확인한다.

파트 글자를 모르면 `docs/TEAMWORK.md` 분담표에서 고친 파일로 찾는다. 그래도 모르면 묻는다.

## 2. 커밋한다

변경 내용을 보고 **무엇을 왜 바꿨는지** 한 줄로 적는다. 팀원에게 커밋 메시지를 지어
달라고 하지 않는다 — 코드를 본 쪽이 쓰는 편이 정확하다.

```
git add -A
git commit -m "feat: 무엇을 왜 바꿨는지"
```

## 3. 옛 버전에서 시작했으면 최신을 합친다

팀원이 며칠 전 받은 코드에서 작업했을 수 있다. 그대로 올려도 PR은 만들어지지만,
같은 파일을 그 사이 누가 고쳤으면 PR 화면에서 충돌로 막힌다. **먼저 합쳐 둔다.**

```
git fetch origin
git merge origin/main
```

**충돌이 나면 혼자 풀지 않는다.** 어느 파일이 겹쳤는지 확인하고:

- **내 파트 파일이 겹쳤다** → 내 작업과 상대 작업을 모두 살려 합친다. 무엇을 어떻게
  합쳤는지 팀원에게 알린다
- **공유 파일이 겹쳤다**(`types.ts` · `store.tsx` · `nav.ts` · `permissions.ts` ·
  `App.tsx` · `shell/**` · `index.css` · `docs/**`) → **내 쪽 수정을 버리고 원격 것을
  받는다**(`git checkout --theirs`). 공유 파일은 리드만 고치기 때문이다. 대신 무엇을
  바꾸려 했는지 「공유 파일 변경 요청」으로 정리해 PR 본문에 넣는다

## 4. 검사한다

```
npm.cmd run typecheck
npm.cmd test
npm.cmd run build
```

**실패하면 올리지 않는다.** 고쳐서 통과시킨 뒤 올린다. 화면을 건드렸으면 미리보기에서
콘솔 오류 0 · 375px 가로 넘침 0도 함께 본다.

`npm.cmd test`는 순수 로직 63건이다(기수 일정 산수 · 권한 판정 · 개인정보 거르기 ·
띄어쓰기 무시 매칭). **그 넷을 고쳤으면 테스트도 함께 고쳐서** 통과시킨 뒤 올린다.

## 5. 올린다

```
git push -u origin (브랜치이름)
```

⚠️ **처음 올리는 팀원은 여기서 GitHub 로그인 창이 뜬다.** 사람이 직접 로그인해야
하므로, 창이 뜨면 팀원에게 "브라우저에 뜬 GitHub 로그인 창에서 로그인해 주세요"라고
알리고 기다린다. 한 번 하면 다음부터는 안 뜬다.

push가 거부되면(`protected branch`) 1번을 안 한 것이다 — 브랜치를 만들어 다시 올린다.

## 6. 팀원에게 알린다

`gh` CLI가 없으므로 **PR은 사람이 브라우저에서 만든다.** push 결과에 GitHub이 주는
링크(`https://github.com/qtg002505/zion-ark/pull/new/(브랜치이름)`)를 그대로 보여 준다.

마지막 보고는 이 형태로 한다:

```
올렸습니다.

무엇을 했는지: (사람 말로 한두 줄)
검사: typecheck 통과 · build 통과

다음에 하실 일:
1. 이 링크를 누르세요 → https://github.com/qtg002505/zion-ark/pull/new/(브랜치)
2. 아래 내용을 본문에 붙여넣고 [Create pull request]를 누르세요
3. 내 파트 파일만 고쳤으면 초록 [Merge pull request] 버튼을 눌러 직접 반영하세요
   버튼이 회색이면 공유 파일을 건드린 것이니 리드에게 알리세요
```

이어서 `.github/pull_request_template.md` 양식대로 **PR 본문을 코드 블록으로** 낸다
(`Closes #이슈번호` 포함 — 이슈 번호를 모르면 묻는다).

## 하지 말 것

- `main`에 직접 커밋·push
- 검사 실패 상태로 올리기
- 충돌을 임의로 뭉개기 — 특히 공유 파일은 원격 것을 받는다
- `git push --force` — 남의 작업을 지운다. 필요해 보이면 리드에게 알린다
- 팀원에게 git 명령을 시키기 — 알아서 하고 결과만 알린다
