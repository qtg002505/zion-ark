# 팀원 작업 절차 — 이슈 하나를 PR까지

팀원이 이슈를 붙여넣으면 이 순서대로 한다. **팀원은 개발자가 아닐 수 있다** —
git 명령이나 파일 경로를 되묻지 말고, 알아서 하고 결과만 쉬운 말로 알린다.

붙여넣은 글에서 아래를 먼저 찾는다. 이슈 양식(`.github/ISSUE_TEMPLATE/`)에 다 들어 있다.

- **담당 파일** — 여기 적힌 파일‘만’ 고친다
- **건드리지 않는 파일** — 읽기만 한다
- **완료 기준** — 체크박스 하나가 커밋 하나의 단위다
- **이슈 번호** — PR 본문의 `Closes #번호`에 쓴다

이슈 번호가 없으면 물어본다. 담당 파일이 안 적혀 있으면 `docs/TEAMWORK.md` 분담표에서 찾는다.

## 순서

**1. 최신으로 맞추고 브랜치**

```
git switch main
git pull origin main
git switch -c part-(a~e)/(요약)
```

옛 코드에서 시작하는 것이 충돌 원인 1위다. `main`에서 바로 작업하지 않는다.

**2. 고친다 — 담당 파일 안에서만**

- 이슈에 없는 기능을 임의로 붙이지 않는다. 필요해 보이면 **먼저 묻는다**
- **완료 기준 하나를 채울 때마다 커밋**한다. 한 번에 몰아서 커밋하지 않는다 —
  중간이 잘못돼도 그 지점으로 돌아갈 수 있어야 한다
- 규칙(불변식·데이터 계약·화면 규칙)은 `CLAUDE.md`에 있고 자동으로 읽힌다

**3. 공유 파일이 필요해지면 — 고치지 말고 적는다**

`types.ts` · `store.tsx` · `nav.ts` · `App.tsx` · `permissions.ts` · `index.css` ·
`shell/**` · `pages/common.tsx` · `components/Accordion.tsx` · `docs/**` · `CLAUDE.md`

이걸 건드리면 **머지 버튼이 잠긴다**(CODEOWNERS). 대신 **"공유 파일 변경 요청"**으로
정리해 PR 본문에 넣는다 — 무엇을 왜 바꿔야 하는지. 리드가 반영한다.

**4. 검증**

```
npm.cmd run typecheck
npm.cmd run build
```

화면을 건드렸으면 미리보기(`.claude/launch.json`의 `zion-ark-dev`)에서 직접 열어 본다.

- 콘솔 오류 0
- 375px 폭에서 가로 넘침 0 —
  `document.body.scrollWidth === document.documentElement.clientWidth`

**통과했다고 말만 하지 말고 실제로 돌린다.** 실패하면 고치고 다시 돌린다.

**5. push**

```
git push -u origin (브랜치이름)
```

**6. PR 본문 초안을 써 준다**

`.github/pull_request_template.md` 양식 그대로. `Closes #번호`를 빠뜨리지 않는다.
초안은 **팀원이 GitHub 화면에 붙여넣을 수 있게** 코드 블록으로 낸다.

마지막에 팀원에게 이렇게 알린다:

- 무엇을 했는지 한두 줄 (파일 이름 나열 말고 사람 말로)
- 검사 결과 (통과/실패)
- **다음에 팀원이 할 일** — "GitHub에 뜬 초록 버튼 눌러 PR 만들고, 아래 본문 붙여넣기"
- 공유 파일 변경 요청이 있으면 그것도 함께

## 하지 말 것

- 담당 파일 밖 수정 (공유 파일은 요청으로만)
- `main`에 직접 커밋·push
- 이슈에 없는 기능 추가
- 검증 건너뛰고 push
- 교리 원문(교안·시리즈·어록) 요약·재작성 — 원문 그대로, 명백한 오탈자만
- 실존 인물 정보를 목업에 넣기 — 수강생 데이터는 전원 가상 인물

## 이슈가 너무 클 때

한 이슈에 일주일치가 들어 있으면 PR도 그만큼 커져 리뷰와 충돌이 커진다.
**어디서 끊는 게 좋을지 제안하고, 첫 덩어리만 먼저 한다.** 나머지는 리드에게
이슈를 쪼개 달라고 요청하도록 팀원에게 알린다.
